Context

FarEye is an enterprise logistics SaaS platform. The clients I work with run inbound, sorting, routing, delivery, returns and customs operations on it, across Southeast Asia and the GCC.

I joined as a Graduate Engineer Trainee in 2021 and have been a Solution Engineer since 2024. Client names are left out on purpose. Every number on this page comes from live client work, not targets.

Problem

Enterprise operations rarely run exactly the way a product expects. Where they didn't match, the same customer issues kept coming back, recurring reporting was done by hand, and feedback took too long to reach a release.

How I framed my job

Find where the product gets in the way of the work, and get it fixed with Product and Engineering.

How I worked

The same loop, client after client.

  1. DocumentWrote down customer SOPs end to end, across inbound, sorting, routing, delivery, returns and customs.
  2. Log the gapsKept a gap register of every place where the workflow and the product didn't match.
  3. SpecifyWrote recurring issues up as proposals with acceptance criteria, as roadmap input for Product and Engineering.
  4. ShipWorked with Engineering on scope, then ran regression and load tests on live production data before go-live.
  5. EnableBuilt a training package for every change, held daily hypercare checks, and coached the client team to run it on their own.

Hardest part: a sorting-machine integration, from scratch

Physical sorting machines and the platform had to agree on every parcel. I designed the integration layer between them, at the boundary where hardware meets software.

  1. API contractsWhat data moves between machine and platform, and in what shape.
  2. Exception handlingWhat happens when a machine reads a barcode the platform doesn't recognise.
  3. ReconciliationHow to catch mismatches between what the machine did and what the system recorded.
  4. Stress testingTesting the whole path at peak throughput before go-live.

Decisions I made

Three calls that changed how the work got done, not just what got built.

DecisionWhyWhat it led to
Made rate card testing a mandatory gate before integration testingFare miscalculations across service type and weight combinations were surfacing later as misattributed SIT failures.Edge cases caught during master data validation, before integration testing.
Built one integration architecture for domestic and international shipmentsThe two journeys each had their own carrier schemas, status events and label formats.A single architecture, plus integration playbooks on endpoints, authentication, payloads and error handling.
Replaced manual rate calculations with a self-service workflowRates were being worked out by hand.Requirements, business rules and acceptance criteria for a rate card and billing dashboard, built with Product and Engineering.
